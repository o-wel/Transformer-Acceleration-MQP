Introduction
	FlashMoE targets the massive communication bottleneck inherent in scaling Mixture-of-Experts (MoE) for LLM inference, where GPU-to-GPU overhead often accounts for 67% to 95% of total runtime. By leveraging a fused kernel architecture and a symmetric heap layout, the system eliminates the need for explicit acknowledgments and avoids write conflicts by design. My findings demonstrate that prioritizing a CP (Consistency and Partition tolerance) configuration within high-reliability HPC environments allows FlashMoE to effectively bypass the traditional constraints of the CAP theorem. This builds directly on the sparse gating logic introduced in the original MoE paper, Outrageously Large Neural Networks: The Sparsely-Gated Mixture-of-Experts Layer [2], while implementing the high-performance communication optimizations detailed in the FlashMoE: Efficient MoE Implementation on GPUs paper [1]. My findings also relate concepts that are vital to FlashMoE success that were introduced in our Distributed Systems course, such as sharding, RPC, and coordinators in MapReduce/GFS.Through these optimizations, the system achieves streamlined token dispatching and expert computation, significantly reducing the latency penalties typically associated with distributed MoE layers. 

Motivation & System Overview 
With the prominence of MoE models, drawbacks have remained as a pain point preventing MoE to be used at scale for LLM inference. One of the biggest drawbacks include the massive communication overhead from GPUs to GPUs. Since each expert in a MoE model is often present on its own GPU, communication from GPU to GPU to move expert weights ends up being the bottleneck, with little actual compute being used. Figure 1 shows the percentage of inference time MoE takes up, which can vary from 67% to around 95% of inference time. 

Figure 1: A trace showing the percentage of inference time on MoE models, with 67-95% of model inference runtime being used for MoE, proving to be a significant bottleneck.[3]

	Tensor cores, which are optimized hardware units in NVIDIA GPUs meant for matrix multiplication, are also underutilized under MoE workloads as well. FlashMoE aims to solve these problems through a concept in GPU programming known as kernel fusion. Kernel fusion aims to fuse multiple kernels into larger kernels that achieve the same tasks as before. FlashMoE effectively fuses 3 operations, MoE dispatch of tokens, Expert communication, and MoE combined into 1 GPU kernel. According to Jonathan Aimuyo, FlashMoE “embeds an Operating System within the kernel, enabling concurrent scheduling and execution, thereby hiding system and communication latency.” [4]
	Figure 2 shows a comprehensive system overview of the FlashMoE architecture. The scheduler, which is part of the “OS” that FlashMoE embeds, is multithreaded, consisting of 1 warp, which is 32 threads of execution. It dynamically assigns tasks to Processor blocks as soon as they become available to ensure maximum GPU utilization. The subscriber, also part of the OS, listens for for incoming tile packets sent from other GPUs, which is then converted into task descriptors that the scheduler can use to get work done on processors. Then, a dispatch tokens layer acts as a router, assigning specific tokens from the input blocks to the appropriate processors, with each processor having its own expert, based on the routing logic learned. Then, each processor receives their dispatched tokens, and then computes a task, such as general matrix multiplication (GEMM). The processor can process the data locally or send the data to the required expert which lives on a different GPU. Once processors finish computations, the results are managed through a tiled output token matrix, A combine tile operation is performed to merge output from different processors into a matrix structure, and the tiled output token matrix is stored in high bandwidth memory (HBM) for the next layer of the model.

Figure 2: FlashMoE Fused Kernel Architecture, including GPU to GPU communication, scheduler, and processing. [4]

In relation to distributed systems, FlashMoE is a prime example of a protocol that ensures multiple processors can communicate effectively to complete a task. We’ve also learned about frameworks such as MapReduce & GFS in class where there is one coordinator or master that makes decisions on what gets executed. FlashMoE operates in a similar manner, where there is a ‘scheduler’ that acts like a coordinator and dishes out tasks for other subscribers and processors to attend to. More concepts of how FlashMoE relates to concepts we learned in class can be found in the analysis section below.



Analysis
	3.1 Distributed Systems Techniques, Source Code, & Comparison to Material
	FlashMoE faces the same fundamental distributed systems challenges we learned in class, including data partitioning, coordination, message ordering, and fault-tolerant communication. This section goes in depth on each challenge and how FlashMoE solved them, pointing to the source code, as well as the comparison to what we learned in class. 

3.1.1 Sharding
	Sharding is just the process of partitioning data across nodes, common among distributed systems when a single node cannot handle the increasingly large volume of data coming in. In large MoE models, such as Llama-4 Scout, there can be up to 16 experts with each expert holding multiple gigabytes of weights for each expert. It is not feasible to store all experts and their weights on 1 GPU and expect exceptional performance. Quantization can help make these weights take up less memory, but not every vendor wants to quantize weights. FlashMoE requires partitioning each expert’s weight matrix across multiple GPUs, where each GPU only computes and stores a subset of any computations. In class, we learned about filesystems and problems with 1 filesystem, which includes needing more capacity, throughput, and fault tolerance. Google filesystem (GFS) solves this problem by sharding file chunks across multiple chunkservers. As a result, FlashMoE and GFS both use sharding to help increase capacity & throughput of their given tasks. FlashMoE does static partitioning, where each GPU hosts numExperts/numGPUs experts. FlashMoE has an expert lookup info (ELI) struct that maps each global expert index to whichever GPU it resides on. Figure 3 shows this struct definition, which is essentially a shard routing table. GFS maps a filename and chunk index to a chunkserver, while FlashMoE maps an expert index to a GPU rank and local index. FlashMoE also uses a Packet Encoding Lookup Info (PEL) struct with memory addresses needed for GPU to GPU communication.
Figure 3: the ELI struct implemented in FlashMoE, located in structures.cuh[4]

	When dispatching tokens, each GPU iterates over all experts and uses the shard table to find out where to send tokens, seen in figure 4.


Figure 4: The code for dispatching tokens, seen in dispatch.cuh. A lookup is first done to see which gpu owns the current expert. Then, a pointer is computed in that peer's memory, and the tokens are copied to that peer’s shard

	FlashMoE’s usage of sharding differs in some aspects to that of GFS. In FlashMoE, there can be gigabytes stored for each shard, while GFS is meant for smaller sizes such as 64 mb. Additionally, in terms of routing, the client has to query the master for chunk locations, while in FlashMoE, each GPU has a full copy of the static routing table. Since the PEL and ELI are replicated across each GPU, there is no need for a querying service as provided in GFS. This eliminates a network round-trip for every lookup but requires all GPUs to have consistent copies. However, this is not an issue for FlashMoE since the map is static.

3.1.2 Centralized Coordinator
	Tokens arrive to GPUs from other GPUs in MoE architectures. When this happens, some thread blocks on the GPU, which are analogous to CPU cores, are idle, while other thread blocks are busy. The scheduler needs to assign the incoming work to available workers. A similar problem exists in MapReduce that the single coordinator must solve. The MapReduce coordinator tracks which map/reduce tasks are pending, and which workers are idle, to then assign tasks to workers. As stated previously, FlashMoE designates one thread block as the "Operating System" (OS) block. Within it, one warp (32 threads) acts as the scheduler, which is a centralized coordinator. This is clearly seen in the code within the one megakernel, which identifies the OS and starts the coordinator, seen in figure 5.
Figure 5: The code shows the logic for starting the OS vs other workers, seen in moe.cuh. The OS is uniquely identified by the GPU block id, while all other blocks begin dispatch to act as workers. A telling sign that the OS logic is here is the os::start call, which starts the OS. [4]

	Once the coordinator is started, one needs to uniquely identify the scheduler and the subscriber, the main aspects of the OS that FlashMoE builds. The logic for this is seen in figure 6, where only 1 warp (warp 0) in the OS acts as a scheduler and the rest of the warps act as subscribers.


Figure 6: In os.cuh, the logic for the scheduler and subscriber is seen in the screenshot above. The scheduler is multithreaded, which is executed by one warp, while the subscriber is executed by all other warps in the current block. We know the scheduler logic resides in the first if statement because there is a clear call to scheduler::start, while the else statement has subscriber::start [4]

	Interestingly enough, the coordinator protocol is very similar to the coordinator in MapReduce. In FlashMoE, workers report readiness by storing a ‘ready’ status in its statusQueue once the worker is free. This is similar to a MapReduce worker sending a heartbeat or "idle" RPC to the coordinator. In processor.cuh, the code says sqd.store(flashmoe::ready,cuda::memory_order_relaxed). Then, the coordinator finds available workers by checking the status queue to find which processors are ready, done by using an atomic compare and exchange protocol to read and reset each solot, which was actually used in our MapReduce implementation in project 2. In processor.cuh, this is seen with: const auto readiness = atomicExch(sQ + idx, observed) == ready; To assign a task, the Scheduler writes a TQSignal (task index + interrupt flag) to the workers’‘doorbell’ using an atomic store with memory_order_release. Workers receive assignments by waiting on its doorbell until the signal changes, seen in figure 7.
Figure 7: In processor.cuh, a worker loads its value by checking its doorbell, and spins in a loop until it receives a valid payload in its doorbell that the scheduler has placed. [4]

	When all tasks are done, the scheduler sends an interrupt to all workers, analogous to the MapReduce coordinator marking the job as complete. One interesting design choice is that the FlashMoE has a work-conserving scheduler, where it will never idle if there are idle processors and pending tasks, which is similar to the MapReduce coordinator. In class, the MapReduce coordinator was its own process on a separate machine. In FlashMoE, the scheduler consists of 32 threads in the OS block, which explains some of the compare and exchange primitives. In task sharing, the MapReduce coordinator sends tasks to workers via RPC, but the FlashMoE coordinator atomically writes a task index to the worker’s doorbell, eliminating the need for RPC in this scenario. Another major similarity is the MapReduce coordinator and FlashMoE’s scheduler are single points of failure in the system. In MapReduce, if the coordinator crashes, then no progress can be made and no new tasks can be scheduled, while in FlashMoE, the whole megakernel hangs if the OS block hangs.

3.1.3 One-Sided Asynchronous Messaging (vs. RPC)
	In standard distributed systems, nodes communicate via RPC, a concept we went over in depth over the course. A client must send a request, the server must process it and send a response. The client must block until the server responds, making the operation synchronous. In standard MoE models, the analogous operation for processor communication is All-to-All, a collective operation in parallel computing where every node or process sends distinct data to and receives distinct data from all other nodes. Every GPU sends tokens to every other GPU and waits for all transfers to complete before computing. FlashMoE aims to overlap communication with computation. Once GPU 0 has received tokens from GPU 1, it doesn’t need to wait for the tokens it sent to GPU 7 to be acknowledged. This can be done with NVIDIA GPUs via NVSHMEM, a scalable and efficient communication procedure for NVIDIA GPUs. NVSHMEM allows for a partition global address space, where memory is logically partitioned but physically distributed across multiple nodes or GPUs. NVSHMEM uses "one-sided" communication. A single GPU can initiate a write or read operation directly to or from the memory of another GPU without that remote GPU's explicit involvement. A standout feature of NVSHMEM is that it allows communication to be triggered directly from within a CUDA kernel. This removes the need to return control to the CPU to manage data transfers, significantly reducing latency and overhead. [5] FlashMoE takes advantage of this by using one sided memory writes instead of two sided RPC communication.The sender writes directly into the receiver’s memory without the receiver’s active participation. This is shown in figure 8.

Figure 8: How FlashMoe uses NVSHMEM for remote direct memory access (RDMA), in dispatch.cu, done by including specifications into a NVSHMEM put signal for writing. Different protocols exist for NVLINK’d GPUs and GPUs who communicate over RDMA, but the premise of one sided communication persists. [4]

On the receiver end, a signal is fetched by accessing the symmetric heap in the case of RDMA, with a simple one liner such as signal = nvshmem_signal_fetch(flags + flagIdx); To ensure data integrity without the overhead of explicit acknowledgments, FlashMoE leverages a release-acquire memory ordering model. By utilizing memory_order_release for signal writes and memory_order_acquire for signal reads, the architecture establishes a strict "happens-before" semantic; this guarantees that once a Subscriber detects a signal, the corresponding token data is already globally visible in memory. Furthermore, the symmetric heap layout (organized by peer, stage, and expert) ensures that one-sided writes remain inherently conflict-free. Since each sender is assigned a unique memory region on the receiver, the system avoids write contention by design. 

	The one-sided communication mechanism employed by FlashMoE contrasts concepts learned in distributed systems. Aside from the one-sided vs two sided communication and the blocking or non blocking calls, there are more differences to be discussed. In RPC, the receiver must accept, process and reply, but in FlashMoE, the receiver only polls a flag to check when the data is available. One benefit of RPC mentioned in class was that it is quite easy to detect failure via RPC timeouts. FlashMoE solves this by using state numbers to detect missed or stale signals, similar to that of a logical clock, a concept we learned in class. One of the biggest benefits of one sided communication that could not be solved by RPC is the straggler problem, which FlashMoE effectively eliminates. If GPU 7 is slow, GPUs 0–6 can still compute on tokens they've already received from each other. 

3.2 CAP Theorem
CAP theory was something mentioned in class, in which a distributed system can often only meet two of the consistency, availability, and partial tolerance requirements. FlashMoE operates where CAP theorem tradeoffs manifest uniquely, prioritizing a CP (Consistency and Partition tolerance) configuration. Eventual consistency is enforced within each epoch via taskBound counters and interrupt mechanisms, ensuring all tiles are processed before completion. While the system sacrifices traditional availability, as a single GPU or network failure will hang the entire job, this is a calculated trade-off optimized for the high reliability of HPC environments and NVLink. Because these networks are essentially partition-free, FlashMoE effectively achieves the benefits of all three CAP properties while maintaining the rigorous correctness required for distributed execution.

Conclusion
While the high latency of distributed MoE models previously made them less desirable for LLM inference, my analysis of the FlashMoE paper and corresponding code proves that kernel fusion and optimized memory communication can effectively dismantle these bottlenecks. We identified three core distributed systems principles that drive this performance, starting with the use of release-acquire semantics to establish a strict "happened-before" relationship for data visibility without high-latency acknowledgments. Furthermore, the symmetric heap layout creates an inherently sharded memory space that allows for one-sided RDMA writes proven to be write-conflict-free. This entire process is orchestrated by an internal OS and Scheduler layer that manages warp-level task decoding and subscriber-driven remote token handling, ensuring that local and remote processing stay synchronized without manual intervention. All 3 methods are proven by analyzing their corresponding code, as the FlashMoE project is open sourced. Finally, we found that FlashMoE deliberately chooses a CP configuration under the CAP theorem; by sacrificing traditional availability for total correctness and leveraging the extreme reliability of NVLink, it effectively operates as if it has all three properties. These findings directly support my future plans to lead the integration of these FlashMoE optimizations into frameworks like vLLM, first by validating these performance gains on the Turing cluster and eventually proving that MoE models can be both outrageously large and exceptionally fast in multi-node environments.
